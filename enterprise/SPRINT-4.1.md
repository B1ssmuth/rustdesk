# YES Desk Enterprise 4.1

Клиент Windows x64 — **1.4.7**, Windows Agent — **1.0.2**. Для администратора нужен клиент с адресом Management API. Для управляемого доменного компьютера нужны клиентская транспортная служба и отдельно установленный агент. Пользователи могут подключаться по YES Desk ID по действующим правилам обычного режима.

## Сборка Windows x64

В Windows PowerShell 7.2+ выполните [подготовку локального инструментального окружения](../docs/YESDESK-WINDOWS-LOCAL-BUILD.md). Подготовьте защищённый файл на основе [примера конфигурации клиента](client-config.example.json). В `YESDESK_MANAGEMENT_URL` укажите пилотный HTTPS URL с доверенным сертификатом и префиксом API, если он используется.

~~~powershell
git switch feature/yesdesk-enterprise-v41
pwsh -File .\scripts\build-windows-local.ps1 -Build -Ref HEAD -EnterpriseConfig C:\Lab\yesdesk-client.json
pwsh -File .\enterprise\agent\Build-Agent.ps1
~~~

Скрипты выводят пути к `YES_Desk-1.4.7-x86_64.msi`, переносимому EXE и `YESDesk-Agent-x64.msi`. Сверьте SHA-256 и используйте принятую в организации процедуру подписания. Клиентский MSI проверяется на единственную службу `YES Desk`, агентский — на `YESDeskAgent`. Идентификаторы продуктов для обновления и пути существующего состояния сохранены. Для прежнего единого пакета используйте [порядок миграции с сохранением идентичности](pilot/EXISTING-INSTALLATION-MIGRATION.md).

## Настройка каталога AD

Запускайте `management/ad_sync.py` из выделенного серверного окружения с теми же версиями зависимостей, что и у API. Примеры unit-файлов находятся в [enterprise/ops](ops). Синхронизатору нужен доступ к PostgreSQL и контроллеру AD через LDAPS. Агент отправляет инвентаризацию только в Management API.

В защищённом файле окружения службы задайте `YESDESK_DATABASE_URL_FILE`, `YESDESK_AD_HOST` (имя из сертификата), `YESDESK_AD_PORT` (по умолчанию 636), `YESDESK_AD_BASE` (область поиска пользователей и компьютеров), `YESDESK_AD_BIND`, `YESDESK_AD_PASSWORD_FILE`, `YESDESK_AD_CA_FILE` и `YESDESK_AD_HOTEL_RULES_FILE`. Дайте отдельной учётной записи права чтения нужных OU и атрибутов `objectGUID`, `dNSHostName`, `name`, `objectSid`, `displayName`. Храните файлы вне Git. Сервисная учётная запись синхронизации в PostgreSQL должна иметь доступ к таблицам снимка и его статуса.

В [синтетическом примере правил](management/testdata/ldap-hotels.json) каждый отель задан полным DN корневой OU. Правило распространяется на дочерние OU. При пересечении действует самое конкретное правило. Компьютеры за пределами правил попадают в «Без отеля». В каталоге администратор может назначить отель зарегистрированному устройству или записи AD без агента и снять ручное назначение. При совпадении записей назначение на зарегистрированное устройство имеет приоритет над назначением на запись AD.

Связь компьютеров устанавливается по уникальному зарегистрированному полному DNS-имени в пределах каждого источника. При дубликате записи остаются раздельными. Текущие активные сессии показываются при heartbeat моложе двух минут. Если SID есть в снимке AD, используется `displayName`, иначе отображается имя из Windows. При сбое импорта предыдущий снимок остаётся доступен с отметкой об ошибке.

### Исправление Sprint 4.1.1

Ответы `searchResRef` пропускаются. Автоматические переходы по LDAP referral отключены. Снимок охватывает записи, которые настроенный контроллер возвращает для `YESDESK_AD_BASE`. Объекты, доступные только через referral, в снимок не попадают.

Для каждой страницы обязательны `searchResDone` с кодом LDAP `0` и управляющий элемент пагинации. Пустой cookie завершает поиск. Ненулевой код LDAP (включая итоговый код `referral`), неожиданный тип ответа, отсутствие cookie и обрыв соединения прерывают импорт. Замена снимка начинается после завершения поиска компьютеров, OU и пользователей. При ошибке записи PostgreSQL откатывает замену.

### Сборка образа Management API на Ubuntu

На Ubuntu с Docker Engine и плагином Buildx выполните в корне репозитория:

~~~bash
set -o pipefail
git switch feature/yesdesk-enterprise-v411-ad-fix
image="yesdesk-management:4.1.1-$(git rev-parse --short=12 HEAD)"
git archive HEAD:enterprise/management | docker build --pull -t "$image" -
docker run --rm "$image" python ad_sync.py --help
~~~

Контекст сборки берётся из коммита. Последняя команда проверяет наличие синхронизатора в образе. Для установки исправления поверх Sprint 4.1 миграция PostgreSQL не требуется.

## Подготовка корпоративного подключения

1. Для нового доменного компьютера создайте одноразовый код через `management/provision.py enroll-windows-device`, используя защищённый JSON с идентичностью устройства. Выполните `enterprise/agent/Provision-Agent.ps1 -Api <HTTPS-URL>` и разверните отдельный агентский MSI. При существующем heartbeat сохраните `agent.token`, MachineGuid, YES Desk ID и транспортные ключи. Приём инвентаризации должен быть включён через `YESDESK_WINDOWS_AGENTS=1`.
2. На целевом ПК получите **публичный** Ed25519-ключ работающей транспортной службы по доверенному локальному каналу. Убедитесь, что он относится к действующему YES Desk ID и системному профилю службы. Храните ключ и параметры устройства в защищённом файле командного оператора. Закрытый транспортный ключ остаётся на целевом ПК.
3. Запустите `python provision.py pin-transport <файл-устройства.json>` в окружении Management API с доступом к БД. Поля файла — `id` (MachineGuid), `dns_name`, `yesdesk_id`, `endpoint_key` (64 шестнадцатеричных символа) и `valid_until` (срок ISO 8601 с часовым поясом). Команда проверяет идентичность и связывает ключ с текущим хешем регистрации. При смене ключа или токена требуется новое назначение.
4. Предоставьте пользователю индивидуальное право через `python local_auth.py grant-device <пользователь> --device-id <GUID>`. Для отзыва используйте `revoke-device`. Убедитесь, что действующая корпоративная политика устройства допускает attended-доступ. `PUT /v2/devices/<GUID>/corporate-policy` принимает `{"attended":true}`.
5. Смонтируйте закрытый Ed25519-ключ подписи Management API как защищённый файл и задайте `YESDESK_CORPORATE_SIGNING_KEY_FILE`. Для первого пилотного ПК можно задать `YESDESK_CORPORATE_PILOT_DEVICE`. Внесите на целевом ПК в защищённую 64-битную ветку `HKLM\SOFTWARE\YES Apart\YES Desk\CorporateSession` значения `DeviceId` (строка с MachineGuid), `ManagementSigningKey` (публичный Ed25519-ключ Management API в hex), `ManagementUrl` (строка HTTPS) и `AllowConsent` (DWORD 1). Проверьте, что права записи выданы администраторам и SYSTEM. Целевой ПК должен быть доступен на активной физической консоли с обычным рабочим столом.

Management API проверяет сессию и индивидуальные права при выдаче и погашении. Разрешение с ограничением до 30 секунд привязано к устройству, транспортному ключу и конкретному рукопожатию. Целевая служба проверяет подпись и запрашивает согласие на текущей консоли Windows. В системном диалоге кнопки «Да» и «Нет» означают разрешение и отказ. Погашение происходит после положительного ответа, а перед началом сеанса проверяется, что на консоли осталась та же сессия Windows. При отказе, истечении разрешения или недоступности API корпоративное подключение прекращается.

## Пилотное обновление Management API

1. На тестовой копии проделайте обновление и откат. Зафиксируйте образы и конфигурации действующего API, точку входа HTTPS и команды возврата на предыдущий upstream. Снимите резервную копию PostgreSQL (`pg_dump -Fc` с проверкой копии через `pg_restore --list`) и отдельно сохраните защищённые файлы конфигурации, ключ MFA, подписи и сведения о сертификатах. Проверьте восстановление в отдельную БД.
2. Соберите образ API из зафиксированного коммита. Запустите из этого образа `python migrate.py` против выбранной БД. Миграция `011_sprint41.sql` добавляет таблицы снимка и ключей, поле отеля и допускает пустую ссылку на сертификат в таблице новых разрешений. Старые регистрации, права, сертификаты и состояние агента сохраняются. Выполняйте миграцию с контролем ожидания блокировок, поскольку изменение схемы кратковременно блокирует затронутые таблицы.
3. Поднимите новый экземпляр **Management API** рядом с прежним за отдельным внутренним адресом или портом и проверьте `/health/live`, `/health/ready`, вход и обновление сессии, импорт AD, heartbeat действующего агента и каталог. Ограничьте первый пилот одним доменным ПК. Оставьте действующие hbbs/hbbr и параметры маршрутизации транспорта на месте.
4. Переключите только HTTPS-маршрут Management API после проверки пилотной пары ПК. Отдельно подтвердите, что открытый сеанс обычного ID-подключения продолжает работать, и установите новое обычное соединение по ID. Сверьте идентичность и heartbeat пилотного агента до и после обновления. Проверьте разрешение, отказ, тайм-аут, отзыв права и отказ при блокировке консоли.
5. Для быстрого отката верните предыдущий upstream и остановите новый синхронизатор. Оставьте расширенную схему и данные на месте. Предыдущий API поддерживает прежние сессии и агентскую инвентаризацию. Корпоративные разрешения Sprint 4.1 перестанут выдаваться и погашаться до возврата согласованных версии API и целевого клиента. Восстанавливайте БД из копии только при повреждении данных после согласования окна и оценки записей, появившихся после снимка.

## Приёмка на Windows

- На ПК администратора установите только клиент. Проверьте обычный ID до входа, отсутствие административных SSH/SFTP/RDP до входа и после выхода, первый вход с TOTP, восстановление сессии после перезапуска, продление access-токена и окончание сессии через 12 часов.
- На отдельном доменном ПК обновите клиентский MSI и агентский MSI по очереди. Сверьте владельца каждой службы, ID и открытый ключ транспорта, запись в Management API, heartbeat и отчёт о сессиях. Проверьте раздельное удаление на снимке VM.
- Проверьте корпоративный запрос на активной физической консоли в светлой и тёмной темах, включая отказ и смену пользователя во время запроса. Запрос использует нативные локализованные кнопки Windows. Для корпоративного сценария нужен интерактивный сеанс физической консоли. Обычный входящий запрос по ID использует штатные кнопки YES Desk.
- Проверьте доменный ПК без агента, ПК со старым токеном, активные сеансы с SID из AD и локальные учётные записи. В рабочей группе проверьте, что агент отклоняет регистрацию и инвентаризацию.

## Автоматические проверки

Запустите `python -m unittest -v test_management test_ad_sync` в `enterprise/management`, используя зависимости из `requirements.txt` и `httpx`. Для PostgreSQL задайте `YESDESK_INTEGRATION=1` и путь `YESDESK_DATABASE_URL_FILE` к одноразовой базе с именем `yesdesk_enterprise_test`. Набор меняет тестовые таблицы. Для полного прогона LDAPS см. [описание синтетических данных](management/testdata/README.md). Для клиента выполните `flutter pub get --enforce-lockfile`, сгенерируйте Flutter/Rust-мост из текущего коммита и запустите `flutter test --no-pub` в `flutter`. Для генерации используйте `-BridgeOnly -Ref HEAD` из [инструкции Windows](../docs/YESDESK-WINDOWS-LOCAL-BUILD.md) и запустите тесты в каталоге снимка сборки. Команда генерации для Linux приведена в [Bridge CI](../.github/workflows/bridge.yml).
