# Simple Enterprise

Обычный клиент по-прежнему обслуживает входящие соединения и подключение по ID. Профессиональные инструменты Windows доступны после входа администратора в Management API. Роль support имеет доступ к каталогу и индивидуальным разрешениям. Корпоративное подключение пока отвечает 501, unattended отключён.

## Безопасное обновление

1. Зафиксируйте текущий образ API, Compose, настройки прокси и рабочие секреты. Создайте резервную копию через `pg_dump -Fc` и проверьте восстановление на временной PostgreSQL 17.9. Проверьте обновление на копии базы и оцените свободное место на Ubuntu.
2. Создайте ключ MFA через `python -c 'from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())'` в приватной оболочке с выводом непосредственно в файл `secrets/mfa-key`. В контейнере этот файл должен читаться UID 65532. Храните резервную копию ключа отдельно от БД. Утрата ключа потребует перезачисления MFA привилегированных учётных записей.
3. Укажите `YESDESK_WINDOWS_AGENTS=1` в отдельном профиле Management API, если требуется принять WTS-агенты. Local auth включена по умолчанию. Для переходного периода прежние OIDC-клиенты используют `YESDESK_LEGACY_OIDC=1` с существующими переменными IdP. Оставьте backend на `127.0.0.1:18083` и существующий TLS reverse proxy. Настройте ограничение запросов аутентификации по источнику на прокси и исключите запись тел запросов и Authorization. API ограничивает число попыток на аккаунт и на весь сервис.
4. В каталоге Management Compose выполните `docker compose build api migrate`, затем `docker compose run --rm --no-deps migrate` на уже работающей отдельной БД. Миграции 004/005 добавляют таблицы и один столбец. Они применяются в транзакции с advisory lock. Затем обновите только API командой `docker compose up -d --no-deps api`. Проверьте `/health/ready`, существующие строки устройств, вход с MFA, отзыв токена и отказ корпоративного подключения. Стеки hbbs/hbbr и RustDesk API обслуживаются прежним Compose.
5. При откате верните образ и конфигурацию API. Добавленные таблицы можно сохранить при откате образа. В случае восстановления базы используйте проверенный backup и отдельно согласуйте потерю записей, сделанных после снимка.

## Локальные учётные записи

В приватном интерактивном терминале без записи вывода запустите `docker compose exec api python local_auth.py bootstrap admin.username`. Пароль вводится скрыто. Первому администратору выдаётся секрет для приложения-аутентификатора. Добавьте его вручную и проверьте вход актуальным шестизначным TOTP. Подключение чужого аутентификатора по серверному выводу даёт право создавать административные сеансы, поэтому передавайте секрет конкретному владельцу по защищённому каналу.

Администратор создаёт пользователей через `POST /v2/accounts`, передавая `username`, `display_name`, `role`, `password`. Действие `PUT /v2/accounts/{username}` с `enabled: false` удаляет все серверные сеансы пользователя. Для admin и support владелец сервера включает MFA в приватной оболочке командой `docker compose exec api python local_auth.py reset-mfa username`. Та же команда используется для восстановления после проверки личности владельца. Она сбрасывает пароль, заменяет TOTP и отзывает все сеансы.

Токен хранится в памяти Flutter и действует 30 минут. Смена пароля и блокировка удаляют серверные сеансы. При недоступном API выход немедленно убирает локальный токен, а серверный токен истекает по своему сроку. Модель не поддерживает публичную регистрацию. Для выдачи или отзыва разрешения оператору используйте `python local_auth.py grant-device USER --device-id GUID` или `revoke-device`. Для доступа к администрированию включите TLS с доверенным сертификатом и соберите клиент с `-EnterpriseConfig` на основе `client-config.example.json`.

## Установка и GPO

Для сборки запустите `pwsh -File .\enterprise\agent\Build-Agent.ps1` в корне репозитория. MSI устанавливает отдельную службу YESDeskAgent с автоматическим запуском. Служба использует LocalSystem для получения SID из токена интерактивного пользователя через WTS. Сведения об идентификаторе RustDesk берутся из записи, подтверждённой оператором при подготовке enrollment. Агент не читает пароль RustDesk.

1. На тестовом ПК получите `MachineGuid` из `HKLM\SOFTWARE\Microsoft\Cryptography`. Получите SID машины из локального SAM через доверенную систему инвентаризации. Проверьте уникальность GUID при клонировании. Сопоставьте его с подтверждёнными hostname, DNS и YES Desk ID.
2. Создайте JSON с полями `id` (MachineGuid), `computer_sid`, `hostname`, `dns_name`, `yesdesk_id`. Запустите `docker compose exec api python provision.py enroll-windows-device /secured/device.json` в приватном терминале. Передайте одноразовый десятиминутный код только этому ПК. Для существующих legacy-строк сохранены данные и режим регистрации. Их перевод в новый режим требует отдельной сверки GUID, SID и YES Desk ID.
3. На ПК выполните `pwsh -File .\enterprise\agent\Provision-Agent.ps1 -Api https://management.lab.example` с повышенными правами. Введите код в скрытом приглашении. Скрипт создаёт защищённый каталог ProgramData. Индивидуальные данные защищены DPAPI и ACL для SYSTEM и локальных администраторов.
4. Установите `msiexec.exe /i YESDesk-Agent-x64.msi`. Проверьте состояние службы, инвентарь, несколько WTS-сеансов, восстановление после потери связи и автозапуск после перезагрузки. При переустановке на том же ПК сохраняйте защищённое состояние. Для ротации остановите службу, отзовите старый агентский токен в Management, удалите старый файл `agent.token` из проверенного защищённого каталога и выдайте новый одноразовый код для той же записи.
5. Для будущего тиражирования назначьте **подписанный** MSI компьютерам на отдельном тестовом OU через Computer Configuration → Software Installation. Разместите его на read-only UNC. Через отдельный защищённый канал передавайте уникальный enrollment в контексте компьютера и запускайте provisioning под SYSTEM. Сам MSI можно тиражировать единым файлом. Коды enrollment следует выдавать по одному на устройство, без открытых скриптов или общих секретов в SYSVOL. Автоматическая выдача кодов доверенным брокером для массового старта остаётся задачей пилота.

Служба получает список сеансов от WTS и обновляет снимок при уведомлениях SCM и heartbeat. История хранит подтверждённое время входа и последнее наблюдение для конкретного сеанса. События, прошедшие целиком во время отключения агента, могут отсутствовать. [Windows WTS API](https://learn.microsoft.com/en-us/windows/win32/api/wtsapi32/nf-wtsapi32-wtsenumeratesessionsw)

Перед пилотом проверьте в двух изолированных VM WTS console/RDP и многопользовательский режим, установку/обновление/удаление MSI, отзыв токенов, загрузку после перезагрузки, TLS и внешний путь входа по HTTPS. Корпоративный запуск остаётся заблокированным до проверки разрешения принимающей стороной, привязки к конкретному каналу и доверенного подтверждения сотрудником.
