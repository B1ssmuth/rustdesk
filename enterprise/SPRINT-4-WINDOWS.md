# YES Desk Enterprise Sprint 4.0

## Сборка Windows x64

Используйте Windows x64 с PowerShell 7.2+, WiX и инструментами из [инструкции локальной сборки](../docs/YESDESK-WINDOWS-LOCAL-BUILD.md). Подготовьте JSON на основе [примера настройки клиента](client-config.example.json). Для прогона задайте HTTPS URL изолированного Management API в поле `YESDESK_MANAGEMENT_URL`. Храните этот файл отдельно от репозитория.

~~~powershell
git switch feature/yesdesk-enterprise-v4
pwsh -File .\scripts\build-windows-local.ps1 -Build -Ref HEAD -EnterpriseConfig C:\Lab\yesdesk-client.json
pwsh -File .\enterprise\agent\Build-Agent.ps1
~~~

Скрипт клиента печатает путь к `YES_Desk-<версия>-x86_64.msi` и переносимому EXE. Скрипт агента печатает путь к `YESDesk-Agent-x64.msi`. Оба скрипта сохраняют SHA-256 в каталогах сборки. Клиентский MSI проверяет наличие только службы `YES Desk`, агентский MSI проверяет свою службу `YESDeskAgent`. Сохранены прежние UpgradeCode обоих отдельных пакетов и расположение каталога агента в ProgramData. При обнаружении старого единого пилотного MSI срабатывает защита от смены владельца службы. Для такой установки нужна [отдельная процедура миграции](pilot/EXISTING-INSTALLATION-MIGRATION.md).

## Проверка на изолированных Windows VM

1. На чистой VM установите только клиент. Проверьте, что `Get-Service 'YES Desk'` находит транспорт, `Get-Service 'YESDeskAgent'` не находит агент, а в тестовом Management отсутствуют heartbeat и инвентаризация этой VM. Проверьте обычное соединение с другой VM через тестовый hbbs/hbbr.
2. Повторите входящий запрос в светлой и тёмной темах. «Разрешить» отображается белым на зелёном и открывает сессию с действующими ограничениями. «Отклонить» выделена цветной рамкой и закрывает запрос. В режиме подтверждения только по паролю кнопка разрешения скрыта.
3. На отдельной VM с уже установленными раздельными клиентом и агентом обновите только клиент. До и после зафиксируйте ID и открытый ключ транспорта, версию и состояние службы агента, успешный heartbeat и событие инвентаризации. Сверьте UID устройства и отсутствие повторной регистрации. На снимке VM отдельно проверьте удаление клиента при установленном агенте и удаление агента при установленном клиенте.
4. На тестовом Management API войдите администратором с паролем и TOTP. Перезапустите клиент под тем же пользователем Windows. Сеанс должен восстановиться, а админские запросы пройти после проверки Management API. Проверьте обновление access-токена и отказ после абсолютного предела 12 часов. Выполните выход, проверьте отсутствие восстановления и HTTP 401 при обращении с отозванным токеном. Повторите проверку после серверного отзыва всех сессий пользователя.
5. Проверьте уже зарегистрированный агент с действующим токеном. Для проверки достаточно существующей регистрации на тестовом Management API.

Для журнала установки Windows используйте `msiexec.exe /i <путь-к-MSI> /norestart /l*v <путь-к-журналу>`. Существующий сценарий `res/msi/test-yesdesk-install.ps1` проверяет клиентский MSI и переносимый EXE на одноразовом Windows runner.

## Сессия Management API

`POST /v2/auth/session` проверяет локальный пароль и существующую политику TOTP. Сервер выдаёт refresh-токен с абсолютным сроком до 12 часов и access-токен до 30 минут. `POST /v2/auth/refresh` принимает refresh-токен как Bearer и возвращает новый access-токен в следующем 15-минутном интервале. Повтор запроса в том же интервале возвращает тот же access-токен. Обновление сохраняет исходный срок сессии. В PostgreSQL хранятся хеши, с использованием существующей таблицы `local_sessions`.

Windows сохраняет только refresh-токен в Credential Manager текущего пользователя, отдельно для каждого HTTPS URL. Выход удаляет локальную запись и запрашивает серверный отзыв. При недоступном API клиент показывает ошибку серверного отзыва, а абсолютный срок сессии продолжает действовать. Смена пароля, отзыв администратором, отключение учётной записи и изменения роли или состояния MFA отзывают сессии штатным способом.

Прежний `POST /v2/auth/login` сохраняет 30-минутный сценарий для старых клиентов. Клиент Sprint 4.0 использует его, если Management API отвечает 404 на новый маршрут. Сеанс на прежнем API хранится в памяти.

Для Windows SSO функция `start_local_session` отделяет выдачу токенов от первичной проверки личности. Будущий провайдер Kerberos должен проверять билет для ожидаемого SPN, сопоставлять проверенный principal с активной локальной учётной записью и выполнять применимую проверку MFA перед вызовом этой функции. Kerberos-вход и интеграция с AD в этот спринт не включены.
