# Sprint 3.8 · Корпоративный доступ и единый пилотный MSI

## Подключения и политики

Подключение по ID использует действующую авторизацию RustDesk. В корпоративном каталоге кнопка «Подключиться» заблокирована. Management API проверяет локальную сессию оператора, роль, индивидуальное разрешение, недавний heartbeat и политику устройства. Если политика разрешает попытку, Management API отвечает HTTP 501. Если политика запрещает её, ответ имеет код HTTP 403.

Для подключения с подтверждением политика по умолчанию разрешает попытки операторам с индивидуальным доступом к устройству. Режим без подтверждения по умолчанию выключен. Его может разрешить администратор для зарегистрированного Windows-устройства на срок до 30 дней. Для попытки по-прежнему нужны роль администратора и индивидуальный доступ. После отзыва регистрации политика удаляется.

Rust-приёмник отклоняет корпоративный запрос до обычной авторизации. Для незашифрованного соединения он требует защищённый транспорт. Для зашифрованного соединения сообщает, что проверка корпоративного доступа недоступна. Перед включением сеансов потребуется привязать одноразовое краткоживущее разрешение к оператору, устройству, режиму и ключам конкретного соединения RustDesk. Принимающая Windows-служба должна проверять локальную политику или подтверждение пользователя до начала управления. Отзыв и истечение разрешения должны прерывать сеанс. Переход на режим совместимости обычного handshake должен закрывать корпоративную попытку.

## Обновление Management

Сделайте резервную копию PostgreSQL и проверьте её восстановление. Примените миграцию 009 на копии базы и выполните интеграционные тесты. Для согласованного тестового обновления запустите команды из каталога отдельного Management Compose.

~~~bash
docker compose build api migrate
docker compose run --rm --no-deps migrate
docker compose up -d --no-deps api
curl -fsS http://127.0.0.1:18083/health/ready
~~~

При откате образа Management таблицу политик можно оставить. Для просмотра условий доступа используйте аутентифицированный GET /v2/devices/{id}/connection-options. Для изменения политики администратор использует PUT /v2/devices/{id}/corporate-policy с полем attended и необязательным unattended_until. Индивидуальные разрешения оператора остаются в существующей CLI. AD по-прежнему служит необязательным источником каталога.

## Сборка и установка на чистой VM

Создайте отдельный JSON-файл с пилотным Management API по HTTPS в поле YESDESK_MANAGEMENT_URL. На обеих VM укажите тестовый ID-сервер, ретранслятор и открытый ключ RustDesk. Используйте изолированную сеть без доступа к производственному серверу, заданному в клиенте по умолчанию.

~~~powershell
pwsh -File .\scripts\build-windows-local.ps1 -Build -Ref HEAD -UnifiedEnterpriseMsi -EnterpriseConfig C:\Pilot\yesdesk-client.json
~~~

Единый MSI устанавливает клиент, транспортную службу YES Desk и службу YESDeskAgent одной транзакцией. При наличии предыдущего продукта, транспортной службы или отдельного агента пакет блокирует первую установку. Для обновления существующих ПК сначала проверьте резервное копирование, миграцию и откат с сохранением служб, конфигурации и состояния DPAPI. Для незарегистрированных клиентов доступна обычная сборка без параметра -UnifiedEnterpriseMsi.

Для каждой чистой VM подготовьте отдельный сертификат компьютера и запись регистрации в рамках пилотной PKI. Запустите enterprise/agent/Provision-Agent.ps1 в режиме сертификата с правами администратора или SYSTEM по инструкции [Unified Workspace](UNIFIED-WORKSPACE.md). Агент использует подготовленную конфигурацию и регистрируется при старте службы. Затем выполните одну установку.

~~~powershell
msiexec.exe /i YES_Desk-Enterprise-1.4.6-x86_64.msi /qn /norestart /l*v yesdesk-pilot-install.log
Get-Service 'YES Desk','YESDeskAgent'
~~~

## Проверка на двух VM перед доменным пилотом

- На чистых VM проверьте установку, запуск обеих служб, регистрацию, инвентаризацию, восстановление после перезагрузки и корректное удаление пакета. На VM с предыдущей версией проверьте, что MSI отклоняет установку и сохраняет службы и конфигурацию.
- Проверьте обычное подключение по ID без корпоративной учётной записи. Для корпоративного каталога проверьте отсутствие запуска сеанса при HTTP 501, отказ при отсутствии индивидуальных прав, истечении политики и отзыве регистрации.
- После реализации проверки на принимающей стороне проверьте согласие и отказ сотрудника, явное разрешение unattended, отзыв во время сеанса, подмену устройства, повтор разрешения, истечение срока, обрыв соединения, блокировку экрана и UAC.
- Для доменного пилота подпишите MSI, согласуйте выпуск сертификатов и сначала разверните на ограниченной тестовой группе. Выход за пределы тестовой группы требует завершённого прогона на двух VM и проверенного отката.
