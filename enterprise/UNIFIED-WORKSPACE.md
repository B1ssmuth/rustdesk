# Sprint 3.7 · Unified IT Workspace

Главный экран Windows открывает единый каталог. Подключение по ID доступно до входа. Администратор после входа попадает в корпоративные устройства. Локальные профили, адресная книга, обнаруженные устройства, избранное и история доступны через представления рабочего пространства. При вводе запроса показываются результаты обоих источников. Стандартный RustDesk использует существующую аутентификацию для локальных профилей. Для корпоративной карточки действие подключения закрыто до проверки на принимающем устройстве. Management API сохраняет отказ HTTP 501 и выключенный unattended.

## Management API

В отдельном каталоге Management Compose сделайте проверяемую резервную копию PostgreSQL. Примените новые миграции сначала на копии БД. После согласования оператор выполняет:

```bash
docker compose build api migrate
docker compose run --rm --no-deps migrate
docker compose up -d --no-deps api
curl -fsS http://127.0.0.1:18083/health/ready
```

Миграции 007 и 008 добавляют данные каталога AD и сведения о предварительно одобренных сертификатах устройств. Оставьте текущие URL Management, сертификаты, MFA и RustDesk Compose. Добавленные таблицы совместимы с откатом на предыдущий образ API.

## Необязательный импорт AD

Запускайте `python ad_sync.py` отдельно от API, например одноразовым заданием контейнера. Предоставьте ему `YESDESK_DATABASE_URL_FILE`, `YESDESK_AD_HOST` (FQDN контроллера с верным TLS SAN), `YESDESK_AD_BASE` (область поиска, например `DC=mcm,DC=ru`), `YESDESK_AD_BIND`, `YESDESK_AD_PASSWORD_FILE` и `YESDESK_AD_CA_FILE`. У сервисной учётной записи должны быть права чтения выбранной области. Храните пароль и сертификаты вне Git. Разрешите сетевой доступ только к одобренным LDAPS TCP 636 и PostgreSQL. Используйте CA организации. [LDAP TLS](https://ldap3.readthedocs.io/en/latest/ssltls.html)

Для ручной синхронизации запустите команду с этой конфигурацией один раз. Для расписания настройте те же команду и секреты в отдельном systemd timer или задании контейнерного планировщика, например каждые 30 минут. При ошибке сохраняется последний успешный снимок. Каталог показывает результат и время последнего успеха. Пустой или неполный LDAP-ответ считается ошибкой, чтобы не стереть снимок при проблеме со scope или правами.

Каталог выводит OU из DN объектов компьютеров. Сопоставление по уникальному FQDN применяется только к отображению. Дублирующиеся имена остаются раздельными. Сопоставление не регистрирует агента, не выдаёт разрешений и не подменяет GUID и YES Desk ID. Локальная авторизация и каталог Management работают без AD и без снимка.

## Индивидуальная регистрация без ручного кода на ПК

Windows Agent 1.0.1 поддерживает прежнюю регистрацию по одноразовому коду и изолированный сертификатный брокер. Брокер работает отдельным процессом `python enrollment_broker.py`, по умолчанию на loopback TCP 18443. Для пилота назначьте отдельный закрытый адрес через `YESDESK_BROKER_BIND`. Настройте firewall и ограничения подключений для пилотных сетей. Брокер должен получать TLS напрямую или через TCP passthrough. Он устанавливает mTLS сам, без передачи доверия через HTTP-заголовки. Требуются `YESDESK_DATABASE_URL_FILE`, `YESDESK_BROKER_CERT`, `YESDESK_BROKER_KEY`, `YESDESK_BROKER_CLIENT_CA` в отдельных защищённых файлах. Для разделения прав дайте воркеру AD доступ только к двум таблицам снимка и статуса. Для брокера выделите роль БД с доступом только к регистрации и аудиту.

Заранее выдайте каждому ПК индивидуальный сертификат с EKU Client Authentication в LocalMachine\My. Закрытый ключ должен быть доступен службе SYSTEM и защищён политикой PKI. Через доверенную инвентаризацию централизованно подготовьте CSV с колонками `machine_guid,computer_sid,hostname,dns_name,yesdesk_id,certificate_sha256`. Последнее поле содержит SHA-256 DER индивидуального сертификата. Импортируйте набор командой `python enrollment_broker.py --approve-csv /secured/approved-devices.csv`. Проверка SHA-256 не заменяет доказательство владения закрытым ключом, которое выполняет TLS. Одобрение действует сутки. При испытании ротации отзывайте прежний токен и одобрение, затем подтверждайте новую запись сертификата.

С едиными **публичными** параметрами установите конфигурацию и MSI из контекста SYSTEM на изолированных тестовых ПК:

```powershell
pwsh -NonInteractive -File .\enterprise\agent\Provision-Agent.ps1 `
  -Api https://management.lab.example `
  -Broker https://enrollment.lab.example:18443 `
  -CertificateIssuer 'CN=Approved Device Issuing CA'
msiexec.exe /i YESDesk-Agent-x64.msi /qn /norestart
```

Служба выбирает единственный подходящий сертификат одобренного издателя. Она генерирует локальный токен, защищает его DPAPI, передаёт брокеру только хеш и использует результат после подтверждения. Повтор после потери ответа допускается только с тем же сертификатом, GUID и хешем. Отзыв агента аннулирует также предварительное одобрение его сертификата. При уже установленной службе с токеном используйте существующую схему обновления, не повторяйте первичное зачисление.

До массового развёртывания проверьте подписанный MSI, реальную выдачу и отзыв сертификатов, mTLS, повтор после потери связи, обновление и удаление службы на нескольких Windows ПК. Сверьте LDAP-результат с пилотным OU предприятия и проверьте поведение без доступного контроллера. Общего enrollment-секрета и ручного ввода каждого кода в сертификатном сценарии нет. Автоматизация зависит от доверенной PKI и централизованного перечня одобрений. Рабочие AD, GPO, DNS и серверы для этого спринта не меняются.
