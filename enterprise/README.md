# YES Desk 3.0 Enterprise Foundation

Текущая настройка локальной авторизации и агента описана в [Simple Enterprise](SIMPLE-ENTERPRISE.md). Этот документ сохраняет историческую схему OIDC и лабораторного агента.

## Компоненты и границы доверия

| Компонент | Назначение |
| --- | --- |
| Существующий YES Desk и hbbs/hbbr | Идентификатор клиента, временный пароль, обычный удалённый доступ, подтверждение, аутентификация и транспорт |
| Браузер + корпоративный IdP | Вход сотрудника через Kerberos IWA в домене или через интерактивную форму IdP |
| Management API | Проверка access token, проверка роли и индивидуальных разрешений, каталоги и аудит |
| PostgreSQL | Привязки SID и `sub`, группы, GUID/SID компьютера, аппаратные данные, журнал сеансов, heartbeat, назначения рабочих мест |
| Windows Agent | Лабораторный прототип индивидуальной регистрации, инвентаризации и передачи событий |

Клиент использует системный браузер, authorization code с PKCE S256, случайный state и краткоживущий callback на `127.0.0.1`. У публичного приложения отсутствует client secret. Flutter получает только access token в памяти и запрашивает роль у Management API. Повторная проверка выполняется каждые 30 секунд; при истечении срока или ошибке проверки клиент возвращается к обычному режиму. Локальный выход стирает токен в памяти, браузерная сессия IdP управляется самим IdP. [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252) · [RFC 7636](https://www.rfc-editor.org/rfc/rfc7636)

API проверяет подпись RS256, доверенный issuer, отдельную audience и срок токена до 15 минут. Значение `sub` связывается с AD SID при импорте каталога. Комплект ролей определяется по трём DN в конфигурации сервера. При каждом запросе API читает членство и проверяет свежесть снимка. По умолчанию снимок действует 30 минут. `admin` видит профессиональные инструменты Windows и каталог, `support` видит корпоративный каталог и может запросить доступ только по назначенным разрешениям, `user` видит базовый клиент. SSH, RDP и RustDesk продолжают проверять свои учётные данные и разрешения.

## AD, Kerberos и интерактивный вход

1. В тестовом OU создайте `YESDesk-Admins`, `YESDesk-Support`, `YESDesk-Users` без привилегий AD. Укажите полные DN в серверном профиле. Зафиксируйте, поддерживает ли ваш поставщик каталога вложенные группы; импорт ожидает эффективное членство с каноническими DN.
2. Подключите выделенный корпоративный IdP с поддержкой Kerberos/IWA. На Windows это может быть отдельно размещённый AD FS. На доменном IdP используйте выделенную сервисную идентичность, при поддержке gMSA. Согласуйте DNS-имя IdP, TLS SAN и уникальный `HTTP/<idp-fqdn>` SPN, зарегистрированный на фактическом владельце службы. В тестовой зоне проверьте тип аутентификации, тикет для нужного SPN, ошибку при неверном SPN и интерактивный резервный вход с MFA. План не требует делегирования. [Microsoft SSPI](https://learn.microsoft.com/windows-server/security/windows-authentication/security-support-provider-interface-architecture) · [Microsoft Kerberos и SPN](https://learn.microsoft.com/en-us/windows/win32/ad/about-mutual-authentication-using-kerberos)
3. Зарегистрируйте OIDC public native client с PKCE S256 и loopback redirect `http://127.0.0.1:<port>/callback` с динамическим портом. Проверьте поддержку этого формата выбранным IdP. Выделите API audience, ограничьте выдачу токенов предназначенными приложениями и политиками IdP, не используйте эту audience для ID token. Интерактивные учётные данные вводятся на HTTPS-странице IdP.
4. Для каталога нужен отдельный процесс авторитетного чтения AD по LDAPS с проверкой CA и имени DC либо SASL/GSSAPI с выделенной read-only идентичностью. Используйте разрешённые базы поиска и атрибуты `objectGUID`, `objectSid`, `sAMAccountName`, `displayName`, `department`, членство в группах, состояние учётной записи. `sub` берётся из подтверждённого сопоставления IdP. В foundation реализован атомарный импорт полного снимка JSON. Возраст снимка настраивается переменной `YESDESK_DIRECTORY_MAX_AGE` в пределах 60–3600 секунд. Автоматический коннектор и проверка доменного входа входят в пилот.

## Лабораторное развёртывание

Работайте в отдельном каталоге развёртывания. Для test, dev и production используйте разные Compose project name, БД, секреты, IdP audience и порты. Для первой лаборатории ориентир 2 vCPU, 4 ГиБ RAM и 20 ГиБ SSD; подтвердите доступность на целевой VM или выберите отдельную VM. Рост определяется сроками хранения событий и аудита. Ни БД, ни PostgreSQL-порт не публикуются.

1. В `enterprise/secrets/db-password` поместите сгенерированный пароль, в `enterprise/secrets/database-url` строку подключения `postgresql://yesdesk:<URL-encoded-password>@db:5432/yesdesk`. Создайте секреты вне Git с ограниченными правами, обеспечьте чтение смонтированного файла UID 65532 контейнера API. В пилоте используйте разные DB роли для миграций, импорта и API, с запретом API изменять группы и назначения и удалять аудит.
2. Замените значения IdP и DN в копии `test.env`, передайте её через `YESDESK_CONFIG`. Запустите `docker compose -p yesdesk-management-test up -d --build --wait`. Проверьте `curl --fail http://127.0.0.1:18083/health/ready`, `/openapi.json` и `docker compose -p yesdesk-management-test logs migrate api`. Профиль test явно включает тестовые credentials агента. Dev и production не принимают их.
3. На отдельном TLS hostname для Management API настройте Nginx reverse proxy к `127.0.0.1:18083` на той же VM. Разрешите только нужные сети, IP ACL и TLS, лимит тела 64 KiB и rate limits для enrollment/запросов. Отключите журналирование заголовков Authorization и тел, отправляйте данные аудита в защищённое хранилище. Если Nginx и Management API на разных VM, используйте приватный TLS upstream и firewall, без публикации backend HTTP. Существующий `desk.yesapart.com`, hbbs/hbbr и lejianwen/rustdesk-api продолжают обслуживаться текущей конфигурацией.
4. Проверьте резервную копию `pg_dump -Fc` с протоколом восстановления через `pg_restore` в чистую БД. Перед миграцией создайте и проверьте backup. Для отката отключите только новый upstream, верните предыдущий образ и совместимую БД или восстановите снимок. Не удаляйте том через `down -v`. Зафиксируйте retention событий и аудита.
5. Создайте публичный JSON по `client-config.example.json` без секретов. Соберите `pwsh -File .\scripts\build-windows-local.ps1 -Build -Ref HEAD -EnterpriseConfig C:\path\yesdesk-client.json` из корня репозитория. Откройте **Настройки → Аккаунт**, завершите вход в браузере. Сборка без файла конфигурации сохраняет обычный удалённый доступ.

## Демонстрация и данные

В изолированной тестовой БД выполните `python provision.py import-directory /secured/employees.json`. Формат снимка: объект с массивом `employees`; запись содержит `sid`, `username`, `display_name`, `department`, `subject`, `group_dns`. Пропущенные сотрудники отключаются в той же транзакции. Обновление отдельно от измерений агента даёт воспроизводимый отзыв роли. Передавайте JSON в контейнер через приватное монтирование или запускайте команду с локальным доступом к тестовой БД.

В профиле test команда `python provision.py enroll-test-device /secured/device.json` принимает `id` (objectGUID), `computer_sid`, `hostname`, `dns_name`, `yesdesk_id`. Источник этих значений проверяет оператор лаборатории. Команда выдаёт одноразовый десятиминутный код для GUID. Повторная регистрация этого GUID с прежними атрибутами отзывает предыдущую идентичность при использовании нового кода. Передавайте код через защищённый канал. Пример запуска на тестовой машине приведён ниже.

```powershell
$api = 'https://management.lab.example'
$id = '<GUID тестового устройства>'
$session = New-Guid
.\enterprise\agent\agent-test.ps1 -Api $api -DeviceId $id -TestEnvironment -Action Enroll
.\enterprise\agent\agent-test.ps1 -Api $api -DeviceId $id -TestEnvironment -Action Heartbeat
.\enterprise\agent\agent-test.ps1 -Api $api -DeviceId $id -TestEnvironment -Action Session -SessionInstance $session -Kind logon
.\enterprise\agent\agent-test.ps1 -Api $api -DeviceId $id -TestEnvironment -Action Session -SessionInstance $session -Kind active
```

Windows-прототип защищает индивидуальный токен DPAPI текущего пользователя, собирает аппаратные характеристики по CIM и прикладывает фактический SID текущего токена Windows и Session ID процесса. Вид события указывает оператор лаборатории. Реальные уведомления WTS, перечисление всех интерактивных/RDP-сеансов, DPAPI системной службы или TPM, автоматическое обновление hostname/DNS и надёжная очередь с повтором входят в пилот. Лабораторная регистрация доказывает владение одноразовым кодом предварительно внесённой записи; доменная идентичность компьютера будет проверяться отдельно.

Карточка сотрудника показывает данные отдельными отметками: последний вход, последнее состояние active, завершение, наблюдение агентом и heartbeat. Активное состояние требует свежести и сессии, и heartbeat. Производственная служба должна получать SID из токена WTS, различать logon generation и переиспользование Windows Session ID, периодически сверять состояние, дедуплицировать повтор по event UUID, поддерживать независимые события нескольких пользователей и ограниченную очередь при сбое API. Инвентарь исключает содержимое экрана, ввода, документов и разговоров.

## Контракт подключения и допуск к пилоту

Management API проверяет корпоративного пользователя и разрешение по GUID, отдельно для consent и unattended. Сейчас даже разрешённый запрос возвращает `501`, а клиент не запускает соединение. Аудит фиксирует отказ или необходимость интеграции endpoint. Раскрытие YES Desk ID в авторизованном каталоге даёт идентификатор для диагностики; этот идентификатор не заменяет корпоративную авторизацию.

Для пилота нужен отдельный проверяемый протокол. После RBAC сервер выпускает короткий, одноразовый grant, привязанный к GUID и ключу устройства, ключу клиента, пользователю, режиму, nonce и конкретному соединению. На принимающей стороне корпоративного запуска проверяются подлинность и актуальность grant, совпадение endpoint и transport binding, одноразовое погашение и локальная политика. Consent требует согласия сотрудника; unattended требует отдельных гранта и политики на конечной машине. Отзыв роли, устройства или политики должен закрывать выдачу и проверку грантов. Текущий RustDesk transport, его аутентификация и шифрование используются для передачи; миграция на корпоративный режим устройства требует проверки прямого запуска по ID и всех альтернативных входов на endpoint. Никаких общих постоянных паролей.

Перед пилотом должны пройти тесты реального AD и IWA, интерактивного входа и отзыва, потери связи и переустановки агента, параллельных console/RDP-сеансов, согласия и отзыва доступа на endpoint, запрета обхода прямым подключением, а также восстановления базы. GPO рассматривается после этих проверок, на отдельном тестовом OU с согласованной политикой и способом удаления.

## Тесты

`python -m pip install -r management/requirements.txt httpx==0.28.1`, затем из `management` — `python -m unittest -v test_management`. Для интеграционных тестов задайте `YESDESK_INTEGRATION=1` и `YESDESK_DATABASE_URL_FILE` для **одноразовой пустой БД `yesdesk_enterprise_test`**. Тесты очищают таблицы этой БД и подписывают JWT тестовым ключом. Верификация реального IdP и AD в этот набор не входит.
