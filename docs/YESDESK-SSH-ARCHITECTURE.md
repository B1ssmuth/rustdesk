# YES Desk SSH Terminal и архитектура модулей

Sprint 1.1 проектирует модули. Текущий переключатель Terminal в сессии RustDesk сохраняет своё действие. SSH, SFTP и остальные планируемые модули появятся в навигации после подключения реальных реализаций.

## Границы модулей

| Модуль | Собственные данные и действия | Связь с рабочим пространством |
| --- | --- | --- |
| Remote Desktop | Существующие Rust FFI, PeerTabModel и диспетчер сеансов | Текущий экран устройств и создание окна RustDesk |
| SSH Terminal | SSH-профили, транспорт, проверка ключей, PTY и состояние терминала | Вкладки с независимыми жизненными циклами |
| SFTP Explorer | SFTP-клиент поверх доверенного SSH-соединения, файловые операции и прогресс | Ссылки на SSH-профили и общая проверка ключей |
| RDP Client | Адаптер платформенного RDP или отдельного движка после оценки лицензии | Отдельный тип профиля, согласие на передачу полномочий |
| Connection Manager | Классификация профилей и отображение локальных состояний активных сессий | Использует идентификаторы модулей. Входящие RustDesk запросы остаются у существующего менеджера |
| Network Tools | Диагностика одного явно указанного адреса и отображение результатов | Самостоятельный модуль без автоматической разведки |

Рабочее пространство предоставляет оболочку вкладок, адаптивную навигацию, локализацию, маршруты, безопасный интерфейс хранилища секретов и уведомления. Каждый модуль предоставляет страницу, допустимые действия и ресурсный контроллер. Идентификатор профиля типизирован по модулю. Секреты хранятся отдельно, а состояние вкладки принадлежит сессии. При закрытии вкладки оболочка запрашивает завершение её ресурсов. Диспетчер RustDesk остаётся на существующем пути запуска.

## Зависимости и совместимость

Проект использует Flutter 3.24.5 с Dart 3.5.4. `xterm` 4.0.0 уже закреплён в `pubspec.lock` и используется действующим терминалом. Его `TerminalView`, `Terminal.onOutput` и `Terminal.onResize` подходят для переиспользования в SSH UI. [xterm 4.0.0](https://pub.dev/packages/xterm/versions/4.0.0)

`dartssh2` 4.1.0 поддерживает Dart 3, но требует `meta ^1.16.0`. Локальная проверка `flutter pub add --dry-run dartssh2:4.1.0` на копии проекта завершилась конфликтом с `meta 1.15.0`, закреплённой `flutter_test` в Flutter 3.24.5. Версия 2.11.0 объявляет `meta ^1.15.0`. Рассматривать её следует только как кандидата для локального прототипа после проверки исправлений безопасности и отличий API. Для продукта предпочтителен отдельный проверенный переход Flutter с актуальной версией SSH-библиотеки. Принудительный override `meta` исключён из плана. [dartssh2 4.1.0](https://pub.dev/packages/dartssh2/versions/4.1.0) · [dartssh2 2.11.0](https://pub.dev/packages/dartssh2/versions/2.11.0)

## Профиль подключения и доверие

Профиль содержит UUID, имя, хост, порт назначения (22 по умолчанию), пользователя, тип аутентификации, ссылку на секрет и параметры терминала. Для состояния доверия используется отдельная запись с каноническим хостом, портом, алгоритмом и SHA256-отпечатком. Регистр букв имени DNS нормализуется. Имя DNS и IP остаются отдельными целями. Импорты профилей проходят проверку и содержат только ссылки на локальные секреты. Учётные данные RustDesk и его серверы в этом процессе не используются.

1. Вкладка создаёт SSH-сокет с ограничением времени и отменой. Каждый клиент явно передаёт `onVerifyHostKey`. В исследованной версии библиотека по умолчанию принимает ключ, когда callback отсутствует.
2. Для известной цели ключ сравнивается с сохранённым отпечатком и алгоритмом до отправки учётных данных. Несовпадение прерывает соединение и показывает сохранённое и полученное значения. Обновление доверия выполняется отдельным действием после сверки по доверенному каналу.
3. Для новой цели диалог предлагает сверить SHA256-отпечаток, доверить этому запуску либо сохранить доверие, если политика разрешает. Отмена и тайм-аут отклоняют соединение. В 4.1.0 callback получает тип и UTF-8 байты OpenSSH-строки `SHA256:<base64>`. Для совместимости с OpenSSH `known_hosts` потребуется отдельная проверка доступа к сырому ключу и формату сертификатов через публичный API библиотеки.
4. После проверки выполняются пароль, приватный ключ или keyboard-interactive согласно профилю. Приватный ключ и passphrase загружаются по запросу. Базовые алгоритмы и их ограничения проверяются до выпуска. Проверка доверия обязательна также для подключений через будущие прокси. [Обработка host key](https://pub.dev/packages/dartssh2/versions/4.1.0#host-key-verification)

## Сессия и терминал

Контроллер ведёт состояния `connecting`, `verifyingHost`, `authenticating`, `active`, `closing`, `closed` и `failed`. Вкладка отображает состояние и предлагает явный повтор. Перезапуск соединения создаёт новый контроллер и повторяет проверку ключа. Одновременно разрешена одна попытка на вкладку. Устаревшие callbacks игнорируются по идентификатору попытки.

- После аутентификации `SSHClient.shell` открывает канал с `SSHPtyConfig`. Отправляются терминальный тип, количество строк и столбцов, а при наличии логические размеры. `Terminal.onResize` вызывает `SSHSession.resizeTerminal` с небольшим debounce после изменения размеров.
- Терминальный ввод преобразуется через UTF-8 в байты SSH. Вывод декодируется потоковым декодером UTF-8 с сохранением хвоста между чанками. Для stdout и stderr используются отдельные декодеры, если сервер возвращает отдельные потоки. Предусмотреть ограничение scrollback, пакетную отрисовку и backpressure. Терминальный вывод не записывается в лог автоматически.
- Ввод с клавиатуры, Ctrl+C, управляющие последовательности, выбор текста, вставка и клавиши навигации остаются под управлением `xterm`. Многострочную вставку следует отдельно подтверждать по политике рабочего пространства. Терминальные escape-последовательности, способные менять буфер обмена или открывать ссылки, требуют явного разрешения приложения.
- При закрытии вкладки отменяются запросы и подписки. Затем закрываются PTY, SSH-клиент и сокет. При обрыве состояния остаются читаемыми до явного завершения. Учётные данные и терминальные буферы освобождаются после использования; Dart не гарантирует затирание всех копий в памяти.

## Безопасное хранение

Профили можно хранить в локальном репозитории данных приложения. Пароли и passphrase передаются через интерфейс `SecretStore` к хранилищам ОС, например Windows Credential Manager или DPAPI в контексте пользователя. Для macOS и Linux выбирать Keychain и Secret Service после проверки упаковки и разрешений. Режим без системного хранилища запрашивает секрет на время сессии. В конфигурации остаются идентификаторы, SSH-отпечатки и несекретные настройки. Логи и crash-отчёты исключают вывод терминала, секреты, приватные ключи и строки профилей, содержащие внутренние адреса.

## SFTP и тесты

`SSHClient.sftp()` в исследованной версии возвращает отдельный SFTP-канал. После оценки транспорта он может работать на доверенном SSH-клиенте либо на самостоятельном соединении с теми же проверками. Задачи загрузки и выгрузки отслеживают отмену, частичные файлы, ошибки авторизации, конфликты и точный прогресс. Операции записи, переименования и удаления требуют выбора цели пользователем. Ссылки и пути нормализуются с учётом поведения удалённого сервера. Серверная файловая система остаётся источником результатов.

Для первой реализации нужны тесты на разбитые UTF-8 последовательности, отмену, повторное соединение, несколько вкладок, отказ и смену ключа, неверные учётные данные, resize PTY, interactive TTY и освобождение файловых ресурсов. Для нативной проверки использовать изолированный согласованный SSH-стенд с предсказуемыми ключами и аккаунтами. Переход Flutter, библиотека SSH и контракт хранилища секретов требуют отдельных проверок до подключения модуля к приложению.
