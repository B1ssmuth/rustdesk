# Корпоративная архитектура YES Desk

Проект следующего этапа. В Sprint 2.1 поставляется SFTP с существующими SSH-профилями. Корпоративная идентификация, регистрация агентов и унификация каталогов потребуют отдельных серверных и клиентских изменений.

## Сервисы и границы доверия

| Компонент | Ответственность |
| --- | --- |
| Identity Gateway | Внутренний HTTPS-вход через SPNEGO/Kerberos для доменных Windows-клиентов, альтернативно OIDC Authorization Code + PKCE через корпоративный IdP |
| Directory Sync | Импорт компьютеров, OU и групп через LDAP с обязательным TLS, включая LDAPS и LDAP с обязательным StartTLS |
| Device Registry | Учёт устройств, привязка объекта AD к подтверждённому агенту и YES Desk ID, жизненный цикл сертификатов |
| Policy Service | Центральное решение о доступе для каждого действия и каждой цели, выдача краткоживущих разрешений |
| Agent Gateway | Регистрация, mTLS, heartbeat, возможности, версия и инвентаризация |
| Session Broker | Проверка каждого запуска и продления сеанса, сверка целевого агента и разрешённого вида доступа |
| Audit Service | Приём, проверка целостности, поиск и экспорт событий с раздельным доступом к аудиту |

RustDesk API остаётся адаптером существующего транспорта. RustDesk ID сам по себе не удостоверяет ни пользователя, ни агент. Прямые способы запуска сеанса с управляемым агентом должны быть ограничены политикой агента и брокера до включения корпоративного режима.

### Идентификация пользователей

1. Windows-клиент получает Kerberos service ticket через SSPI для SPN `HTTP/<fqdn>` сервиса входа. Gateway проверяет билет для собственного SPN и корректность TLS-привязки там, где её поддерживает конфигурация. Сервис работает под gMSA или с защищённым keytab. Автоматический переход на NTLM выключен.
2. При входе через IdP клиент открывает системный браузер, передаёт PKCE, state и nonce. Gateway проверяет подпись, issuer, audience, сроки и привязку к tenant. Сопоставление с AD возможно через доверенный immutable ID или утверждённую администратором связь. Имя и email отображаются независимо от идентификаторов, используемых при проверке прав.
3. Gateway выпускает короткую сессию с внутренним UUID пользователя, источником идентичности, временем аутентификации и версией политики. Обновление токенов использует ротацию. Выход, отзыв и блокировка учётной записи действуют через серверную проверку.
4. Домен и группы хранятся вместе с неизменяемыми идентификаторами. Вложенные группы раскрываются на сервере. Изменения состояния учётной записи и членства инвалидируют кэш решений и блокируют новый доступ в пределах установленного SLA.

### Регистрация устройства

1. Directory Sync создаёт запись компьютера со стабильным `objectGUID` в пространстве соответствующего AD forest. Отдельно сохраняются SID, DN, состояние объекта, OU, подразделение, источник и дата последней сверки.
2. При развёртывании агент создаёт ключ на устройстве, предпочтительно в TPM или защищённом хранилище ОС. Администратор или система развёртывания получает одноразовое приглашение, привязанное к записи компьютера, сроку действия и области регистрации.
3. Gateway проверяет приглашение, подпись challenge и подтверждение доменного компьютера от доверенной системы развёртывания. Транзакция использует приглашение ровно один раз, связывает публичный ключ, UUID агента и заявленный YES Desk ID, затем выпускает клиентский сертификат. Зарегистрированный YES Desk ID не может автоматически перейти другому агенту.
4. Повторная установка и смена агента требуют новой санкционированной регистрации с отзывом старой привязки. При переносе компьютера между OU переоцениваются ACL. Удаление и отключение объекта переводят устройство в карантин. Отзыв, ротация сертификатов и статус доверия отражаются в аудите.

## Хранение и авторизация

Использовать транзакционную реляционную БД. Ключевые сущности — `tenant`, `identity`, `directory_object`, `directory_membership`, `role_mapping`, `device`, `agent_identity`, `device_scope`, `policy_grant`, `session_grant`, `inventory_snapshot`, `audit_outbox`. Внешние связи ограничены tenant. Уникальные ограничения защищают активную связку AD-компьютер ↔ агент ↔ YES Desk ID и погашение приглашений. Сертификаты и сервисные секреты хранятся отдельно от прикладных данных.

| Роль | Область |
| --- | --- |
| IT Administrator | Настройка каталога и политики, регистрация и отзыв агентов, делегирование прав в разрешённой области. Изменение критических политик требует второго утверждения |
| Support | Просмотр назначенных групп устройств, разрешённый вид удалённого доступа, инвентаризация в пределах предоставленного scope |
| Employee | Просмотр собственных или явно назначенных устройств и запрос помощи. Запуск сеанса возможен только при отдельно предоставленном праве |

Сопоставлять роли со специальными группами AD по SID и идентификатору леса. Для IdP использовать явно утверждённые связи с корпоративными группами. ACL хранит principal, разрешённые действия и scope из OU, управляемой группы устройств или явного списка. Действие разрешается при совпадении tenant, роли, grant и scope, действующем доверии агента и выполнении ограничений политики. Явный запрет имеет приоритет. По умолчанию доступ закрыт. Фильтры списка, поиск, API инвентаризации и брокер используют тот же вычислитель решений. Каждое разрешение сеанса связывает пользователя, агента, действие, срок и одноразовый nonce. Агент проверяет подпись, audience, срок и подтверждение через брокер.

### API и жизненный цикл данных

- Пользовательские маршруты `/auth/kerberos`, `/auth/oidc/callback`, `/auth/refresh` и `/auth/logout` выдают и отзывают сессию. Сервис политики проверяет её при каждом защищённом запросе.
- `/v1/devices`, `/v1/devices/{id}/inventory` и `/v1/org-units` возвращают только видимые пользователю записи. Серверная пагинация выполняется после применения политики. Последний heartbeat отличает доступные, просроченные и отозванные устройства.
- `/v1/enrollment`, `/v1/agents/heartbeat` и `/v1/agents/inventory` разделяют начальную регистрацию и вызовы по mTLS. Принимаются ограниченные версионированные схемы. Сервер связывает данные с идентификатором сертификата.
- `/v1/sessions` выполняет авторизацию, выдаёт одноразовое разрешение и регистрирует старт, продление, отказ и завершение. Административные маршруты управляют ролями, группами устройств, приглашениями и отзывом с оптимистичной проверкой версии.
- Directory Sync имеет выделенную учётную запись только для чтения, проверяет сертификаты контроллеров, использует постраничную выборку, изменения по допустимому AD-механизму и периодическую полную сверку. Checkpoint хранится на сервере. Неполная синхронизация не удаляет устройства. Перед массовым выводом устройств из эксплуатации применяется карантин и проверка полноты снимка.
- Позволять агенту передавать версию ОС, версию агента, базовую аппаратную сводку и разрешённые поля. Отдельная политика задаёт период и сроки хранения, включая удаление устаревшей инвентаризации.

## Аудит и отказоустойчивость

Фиксировать аутентификацию, разрешения и отказы, изменения ACL, выдачу и отзыв сертификатов и начало/конец сеансов. Событие содержит actor, действие, target, результат, correlation ID и версию политики. Использовать транзакционный outbox и отправку в append-only хранилище с контролем целостности и сроком хранения. Пароли, ключи, токены и содержимое удалённых файлов исключаются из событий.

При недоступности DC приостановить регистрацию, каталог и повышение прав. Помечать представление устройств временем последней успешной синхронизации. Доступ пользователей с действующей сессией и последним подтверждённым набором прав разрешать только в коротком окне, заданном политикой. После окна запретить новые сеансы и продления. OIDC-вход возможен при доступном IdP, с применением того же ограничения свежести каталога. Аварийные учётные записи независимы от DC, защищены MFA и хранятся вне обычного процесса входа. Доступ ограничен заранее определёнными устройствами, временем и двойным утверждением. События сохраняются локальным надёжным outbox. После восстановления выполнить полную сверку и отозвать аварийные разрешения.

## Миграция

1. Развернуть Gateway, Directory Sync и реестр за флагом. Проверить импорт в режиме чтения и разрешить неоднозначные сопоставления.
2. Зарегистрировать пилотные агенты, сверить дубликаты и конфликтующие YES Desk ID. Добавить проверку корпоративного разрешения на управляемых агентах.
3. Сопоставить AD-группы, запустить теневое сравнение решений и сценарии отказов. Включать обязательную серверную авторизацию по согласованным группам устройств после проверки отказов и аудита.
4. После корпоративного входа объединить «Адресную книгу» и «Доступные устройства» в «Корпоративные устройства». Импортировать проверенные заметки и избранное отдельно от ACL. Сохранённый адрес сам по себе не создаёт корпоративного grant. Сохранить обратимые сопоставления старых записей с UUID устройств на переходный период.
5. При откате отключить новый интерфейс и приостановить импорт. Центральные проверки управляемых агентов сохраняются до санкционированного изменения политики. Архивировать журнал миграции и сохранить возможность восстановления регистраций.
